# 牌谱回放内纠错：需求与验收

版本：v1.1 · 2026-09-10

状态：首版 A、B、C 已实现；关联摸打选择、失败诊断和成组撤销已补齐并验收（2026-09-10）。限本地血战赛事原谱。视频内容逐项核验仍未完成。

## 1. 要解决的问题

用户在 DSH 对照录像发现错误，需要直接在当前回放里更正，并立即看到由新记录生成的牌桌。现在修改原始 JSON 后，还要人工校验、生成快照、同步案例、重启服务，容易出现文件已改而界面仍旧的问题。

**功能名称：牌谱纠错。首版目标：不离开 DSH、不手改 JSON、不运行命令，完成“定位错误 → 编辑 → 校验 → 保存并更新回放 → 必要时撤销”。**

这是更正历史记录，不是模拟另一种出牌。假设出牌和挑战分支另存，不能覆盖历史牌谱。

首版现已接入编辑、草稿保存、校验预览、版本提交和同牌桌加载确认。后续版本范围见第 8、9 节。

## 2. 首版范围与入口

- 首版覆盖目前使用的血战到底赛事牌谱；先以现有 S6 案例验收，再用一份不同动作数量、不同结算结果的血战案例验证通用性。国标纠错随后接入对应规则与牌张格式，首版不得把它套进108张血战校验。
- 在现有回放工具栏增加“纠正牌谱”，点击后暂停播放，打开 DSH 内的编辑面板。默认定位当前步骤、实际行动玩家和对应事件；观察视角不决定修改哪位玩家。
- 面板展示“回放第47步／行牌事件44／龙公子／弃牌／02:47.5”，避免把界面步骤与事件编号混为一谈。换牌前、换牌后、定缺等阶段使用明确名称。
- 通过面板编辑，不要求首版在3D牌桌上新增点牌事件。直接点击牌河定位对应记录作为后续便捷功能。
- 保留真实 MJLab 牌桌及1280×720等比显示；不新增实体牌墙。面板可使牌桌等比缩小，但不得裁切或重排游戏内部元素，也不得替换原生对话区。
- 操作按钮为“保存草稿”“校验并预览”“保存并更新回放”“取消”。保存前展示改前、改后和受影响范围，不叠加重复确认弹窗。

## 3. 能修改什么

| 类别 | 首版要求 | 保存约束 |
| --- | --- | --- |
| 玩家与开局 | 昵称、座位对应、庄家、换牌前手牌 | 显示明确玩家；改座位要检查全部事件归属，不只换标签 |
| 换三张 | 每家送出的三张、接收对象或换牌方向 | 三张必须来自该家手牌，按已选规则检查花色及收发数量 |
| 换牌后手牌 | 展示计算结果，允许录入视频中看到的实际手牌作为核对记录 | 有差异时定位起手牌或换牌记录；不能暗中反推修改起手牌 |
| 定缺 | 四家各自定缺花色 | 用“缺条／缺筒／缺万”，不要求用户输入代码 |
| 行牌事件 | 摸牌、弃牌、碰、明杠、暗杠、补杠、杠后补牌、点炮胡、自摸；行动玩家、牌张及关联来源 | 修改响应动作须明确来自哪次弃牌或哪组副露；不能只改提示文字 |
| 漏记与多记 | 插入、删除、调整动作顺序 | 必须属于首版，否则无法修正漏摸、漏胡和多余弃牌；删除后检查被引用动作 |
| 积分 | 初始记录分数、具体转账的付款方／收款方／分数 | 终局积分由初始值及转账计算，不能单独改总分掩盖转账错误 |
| 来源 | 原视频时间点、截图或文字依据、修正说明、证据状态 | 标明用户更正、直接观察、连续状态推定或未核实，不能自动升级为已核实 |

所有编辑面板的手牌列表以及导出的 `dealtHand`、`openingHand`，按“条 → 筒 → 万，同花色一至九”排列，重复牌相邻。排序只影响阅读顺序，不改变牌张身份、摸牌次序或余墙顺序，也不借此重排现有3D牌桌。

兼容现有字段含义：`dealtHand` 为换牌前；`openingHand` 为换牌后；`dingque` 为定缺。UI直接显示中文名称。

## 4. 一份原始记录，派生全部回放

原始牌谱是唯一可提交的历史事实数据源。手牌快照、牌河、副露、赢家列表、余牌计数、步骤文字和最终积分均由同一版本生成，不允许分别保存两套互不检查的事实。

- 从换牌前手牌、换三张及后续事件计算状态；保存的换牌后手牌必须与计算结果一致。现有双字段导入不一致时报告差异，不静默选择一方覆盖另一方。
- 数据来自推定时保留推定来源。把换牌前手牌设为计算起点，不代表它已由视频直接确认。
- 用户只修改第44事件“弃七万”，而此前只有“摸五万”时，界面报告“龙公子当前手中没有七万”，提供跳转第43事件的入口。用户可在同一草稿把第43事件改成“摸七万”，两项合并校验、提交。
- 不自动把所有五万替换成七万，不自动改尾墙、其他玩家或后续动作来消除矛盾。
- 增删动作使用稳定事件标识关联碰杠胡、问答和讲解。显示编号可以重排，已有引用不能仅靠数组下标维持。
- 支持从第一位赢家继续记录第二、第三位赢家；第三家胡牌或规则规定的流局条件结束本副。保存全部胡牌顺序、来源和转账，不能在第一次胡牌时截断后续。

## 5. 校验结果必须分清两层

### 数据与规则一致性

检查格式、花色与张数、起手数量、换牌收发、行动轮次、手中是否有弃牌、定缺要求、碰杠胡的来源和条件、杠后补牌、已胡玩家退出、胡牌形、积分转账及牌张守恒。每个有问题的结果指出玩家、最早发生的步骤、实际缺少或多出的牌，以及可跳转的原始记录。

“超过同名4张”等物理矛盾阻止提交为可用回放。规则相关校验取决于绑定的赛事规则；规则未确定的项目显示“该规则尚未校验”，不得用产品默认番型覆盖赛事记分。

原谱记分采用已记录转账时，检查转账有效性和合计；不宣称赛事完整计分规则已验证。不能硬编码所有案例都应有84条动作、19张余牌或固定的最终分数。

### 原视频证据核对

程序校验通过仅说明记录内部能够成立，不表示识别了正确牌面。每次编辑和关键核对记录分别保存证据状态；自动生成的后续快照不会因此变成“已对照视频”。

编辑面板可打开已关联的本地视频并定位该步时间；视频未关联时允许补选文件或先保存草稿，不能标记为已看过视频。首版不要求上传完整原视频到云端。

支持在选定步骤录入独立的“视频实见手牌／牌河／副露”核对记录，带玩家、时间和可见范围，再与计算状态比较。不能把计算出来的快照复制成所谓独立观察证据。遮挡和未见部分保留未知。

允许提交结构有效但证据未全核实的本地回放，界面持续标明“视频核对未完成”；不得进入“已核实案例”或自动恢复相关讲解、视频和挑战。

## 6. 草稿、预览与生效

流程：进入纠错后暂停播放 → 在草稿中修改一项或多项 → 校验并查看预览 → 保存为新版本并更新当前回放。

- 修改摸牌牌张时，如果下一事件是同一玩家的弃牌，先提供“只改摸牌”“摸打都改为所选牌”“取消这次修改”。选择之前不改动草稿；原摸牌与原弃牌可以不同，由用户根据视频决定。杠后补牌也适用；不跨过碰杠胡或其他事件寻找弃牌。
- “摸打都改”只修改明确展示的两条事件，作为一组撤销／重做。不会更改其他动作、起手牌、尾墙或证据状态。每次应用后仍可继续改其他事件，一并校验、提交。
- 有冲突时仍可保存草稿，关闭、刷新或重新打开后可恢复。草稿不覆盖当前可用版本。
- 全部撤销回到原记录也必须替代此前保存的草稿；关闭重开不能恢复已撤销内容。同一编辑窗口按序保存，恢复时优先保留浏览器中的最新草稿，服务器草稿作为本地缓存不可用时的恢复来源。
- 校验失败时，显示首个被校验器发现的错误、相对于草稿基础版本修改过的事件及开局信息，并提供事件跳转。可比较时，展示同一出错动作执行前双方暗手的差异，例如“多1张五万、少1张七万”。错误被发现的位置不等于最初记错的位置。
- 建议检查的关联步骤只作为排查线索，不声称已确定根因，不自动代改。没有可比状态时不推测缺牌。跳转检查保留上次失败提示，实际修改后清除旧结果，需重新校验。
- 草稿预览醒目标明“未生效”。存在矛盾时可展示首个错误之前可计算的部分；不能虚构错误之后的完整牌桌。
- 校验通过后，在服务端一次性保存原始记录、新版快照、版本信息和审计记录，再切换当前版本。任一生成或写入失败，保留原可用版本，给出实际失败原因。
- 成功后同一牌桌加载新版数据，停留在对应事件和原观察视角，保持暂停，不要求重启 Harness、运行脚本、重新开桌或重新进赛事目录。
- 删除了当前事件时，定位到前一个仍存在的事件，并说明定位变化。
- “已更新回放”必须等待客户端确认已加载新版本及新画面；仅写入文件但加载失败时，显示“已保存，回放加载失败”，提供重试。
- 保存期间保留用户输入；连续点击保存不得生成重复提交。保存后明确显示版本和本次修改摘要。

## 7. 撤销、外部修改和已有内容

- 编辑中的撤销／重做只影响草稿；关联摸打一次撤销即恢复两步，一次重做即重放两步。该操作历史限本次打开的编辑面板，刷新可恢复草稿但不恢复撤销栈。正式版本可查看修改前后差异。恢复旧版本生成一次新的恢复记录，不删除中间历史。
- 保存携带基础版本。其他窗口或外部JSON已修改时，拒绝静默覆盖，展示冲突并允许保留、导出当前草稿。
- 保留外部JSON编辑方式。在案例内提供“重新读取源文件”：读取后先显示改动与校验结果，再应用；不自动覆盖外部更正。刷新文件列表不等于提交新回放。
- 同一原始文件只登记一次，显示当前实际来源位置。新案例采用项目可管理的位置，不依赖某次 Codex 任务目录；旧案例可登记现有路径，不擅自移动用户文件。
- 回放更新不重写旧问答。旧问答绑定旧版本并显示版本提示；新问题使用当前已加载的新版本和事件。
- 修改影响手牌、弃牌、规则或分数时，相关关键步分析、讲解、视频和挑战标记为“需重新核对”。旧文件保留，禁止静默关联为最新成果；首版可保守地让该案例全部分析失效。
- 已开始的挑战固定原版本，不中途换牌；新挑战入口在关联分析失效后暂停，复核后重新开放。未实现的挑战不伪造上线状态。

## 8. 本地与 Cloudflare 的范围

编辑及生成使用相同的规则和版本格式，存储方式分别适配：本地写项目管理的记录及版本文件；Cloudflare 通过服务端版本存储提交，浏览器不传任意文件路径，也不依赖在 Worker 内运行本机脚本。

建议首版先完成本地DSH完整闭环，并将“云端纠错”单列为后续未完成项；这不改变项目原有本地／云端部署目标。

统一部署时只有案例维护者可修改官方案例；普通观众可以“复制到我的牌谱后编辑”或提交纠错意见，不能改共享原件。自部署时部署者管理自己的案例。没有修改权限时不给可生效的编辑入口，服务端也必须拒绝未授权提交。

## 9. 开发拆分

| 阶段 | 内容 | 完成标准 |
| --- | --- | --- |
| 首版A：数据闭环 | 原谱登记、通用校验与生成、版本保存、原子切换、失败回退 | 更正可从原谱一致生成所有状态；任何失败不破坏旧版 |
| 首版B：回放内编辑 | 中文编辑面板、单项及关联修改、增删动作、草稿、预览、保存和即时加载 | 用户在DSH内完成纠错，不依赖命令或手工同步 |
| 首版C：可信核对 | 原视频定位、实见状态核对、来源标记、差异与错误定位、撤销恢复、外部修改冲突 | 原始观察与推定分开；版本和错误可追溯 |
| 后续 | 直接点击牌桌定位事件、云端纠错、多人协作、国标适配、辅助识别 | 分别设计与验收，不计入首版已完成 |

首版A、B、C全部通过才可宣布“回放内纠错已完成”。OCR、AI自动修正整副牌、自动发布视频和挑战不属于此首版。

现有实现需调整的边界：将任务工作目录中的校验、生成脚本移入项目成为通用能力；扩展现有赛事案例目录、接口和回放控制器以支持版本加载；保持插件边界，不修改Harness核心。原生成快照只作为缓存，不能成为第二个手工编辑源。

| 20 | 恢复旧版本基础的草稿，或插入、删除事件 | 诊断对照草稿基础版本，以稳定事件标识匹配；不把编号顺延当成全部事件已改 |

## 11. 当前状态与既有流程的关系

当前已实现回放内纠错面板、稳定事件引用、原谱生成、草稿恢复、版本提交与恢复、外部改动冲突保护、视频定位和独立实见核对；保存后由同一个牌桌确认加载，不需重启。17 项纠错自动测试及 2 项接口边界测试通过，插件共 130 项测试通过；前端检查与独立/嵌入构建通过。DSH 实测完成关联改牌预览、缺牌拒绝、刷新恢复、实见不符、撤销/重做、视频定位、版本列表、画面确认失败与重试、不同观察视角保存。首版 16 项验收由上述自动测试与实际界面验证覆盖。

2026-09-10 增补验收：插件共 143 项自动测试通过（相对此前135项新增8项），覆盖关联选择、草稿保存恢复及修复后提交、旧基础版本诊断、稳定事件匹配、异常输入和接口边界。Ego Lite 实测“只改摸牌→校验失败→跳转下一弃牌→保存草稿→刷新恢复→补改弃牌→校验成功”、两步成组撤销／重做及取消不修改通过；1143×925窗口面板无横向溢出，牌桌保持16:9。此次使用独立测试草稿，正式v6原谱及已安装回放文件保持不变。新增功能不代表已完成视频逐项核验。
